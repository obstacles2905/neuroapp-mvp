# Замер голоса и эмоций (аудио + openSMILE)

Документ фиксирует **бизнес-смысл**, **границы продукта** и **техническую архитектуру** голосового биозамера. Цель замера — не медицинская диагностика, а воспроизводимая оценка голосовых маркеров, которые могут коррелировать с эмоциональным напряжением, неуверенностью, зажимами гортани и стрессовой реакцией.

---

## 1. Бизнес-логика (кратко)

- Замер голоса — **динамический маркер состояния**, а не разовый профиль личности. Важна история: baseline пользователя, отклонения от себя, тренд после практик.
- Пользователь проходит **короткий протокол записи**: одинаковая фраза, свободная речь и/или удержание звука. Это снижает шум и повышает сравнимость сессий.
- На выходе нужны не сырые аудиофичи openSMILE, а **продуктовые метрики методики**: стабильность голоса, напряжение, дрожание, монотонность, уверенность речи, эмоциональная окраска.
- **Приватность по умолчанию:** аудио анализируется на устройстве; на сервер отправляются только агрегаты, quality flags, версия конфигурации openSMILE и идентификатор замера.
- Результат должен подаваться как **вероятностная подсказка**, а не диагноз: "есть признаки повышенного напряжения в голосе", а не "у пользователя тревожное расстройство".

---

## 2. Что реально измеряем

| Бизнес-сигнал | Технические признаки | Продуктовая интерпретация |
|---|---|---|
| Зажимы гортани / напряжение | F0 contour, jitter, shimmer, HNR, spectral slope, voice quality features | Голос звучит с повышенной нагрузкой или нестабильной фонацией. |
| Дрожание голоса | Микровариативность F0, jitter, amplitude modulation, voiced segment instability | Возможный маркер волнения, усталости или мышечного напряжения. |
| Неуверенность | Паузы, темп речи, доля voiced/unvoiced, громкость, монотонность, pitch range | Пользователь говорит менее устойчиво, с большим числом пауз или узким диапазоном интонации. |
| Эмоциональное напряжение | eGeMAPS / ComParE признаки, prosody, energy, spectral features | Агрегированный индекс эмоциональной активации. |
| Эмоциональная плоскость / подавленность | Pitch range, energy range, speech rate, monotonicity | Низкая выразительность и малый интонационный диапазон. |

openSMILE извлекает акустические признаки. Связь этих признаков с психологическими состояниями должна валидироваться на наших данных и не должна описываться в UI как клиническая истина.

---

## 3. Три слоя данных (контракт мышления)

| Слой | Содержимое |
|---|---|
| **Наблюдение** | Аудиозапись, длительность, sampling rate, устройство, уровень шума, протокол задания, таймстемп. |
| **Инференс** | openSMILE feature vector, config name, config version, extractor version, frame/window параметры. |
| **Продукт** | Нормализованные метрики, quality score, интерпретация, рекомендации для UI, sync payload. |

Смена конфигурации openSMILE или формул нормализации может ломать сравнимость. В каждой записи нужно хранить `extractorId`, `extractorVersion`, `featureSet`, `scoringVersion` и `protocolVersion`.

---

## 4. Протокол записи

### 4.1. Базовый сценарий

1. Пользователь даёт permission на микрофон.
2. Приложение проверяет шум окружения 1-2 секунды.
3. Пользователь записывает короткий набор:
   - **Sustained vowel:** удержание звука "А" 3-5 секунд для jitter/shimmer/F0 stability.
   - **Fixed phrase:** одинаковая фраза 5-10 секунд для сравнимости.
   - **Free speech:** свободный ответ 15-30 секунд для темпа, пауз, уверенности и эмоциональной окраски.
4. Клиент проверяет качество: длительность, clipping, speech presence, SNR, долю тишины.
5. openSMILE извлекает признаки.
6. JS-слой рассчитывает продуктовые индексы и сохраняет сессию локально.
7. При готовности API клиент синхронизирует только агрегаты.

### 4.2. Почему не одна произвольная запись

- Разные фразы дают разные pitch/energy профили и хуже сравниваются.
- Шум, микрофон, расстояние до телефона и усталость сильно влияют на признаки.
- Удержание гласной лучше подходит для фонации, а свободная речь — для уверенности, пауз и эмоций. Нужны оба режима.

## 5. Техническая архитектура в репозитории

### 5.1. Где живёт openSMILE

- Базовый путь — **on-device inference** через нативный модуль, потому что голосовые данные являются чувствительной биометрической информацией.
- openSMILE — C++-инструмент; JS не должен выполнять DSP. JS-слой только управляет записью, вызывает нативный extractor и считает продуктовые агрегаты.
- Для первого прототипа допустим backend/Python extractor только как исследовательский стенд, но не как основной production flow без явного пользовательского согласия на загрузку аудио.

### 5.2. Expo / React Native

- Как и с MediaPipe, кастомная нативная интеграция не работает в Expo Go. Целевой цикл: development build / EAS Build.
- Для записи можно стартовать с `expo-av`, но архитектурно держать `AudioCaptureAdapter`, чтобы позже заменить реализацию на нативный recorder с более строгим контролем PCM/WAV.
- openSMILE лучше кормить нормализованным WAV/PCM: mono, 16 kHz или 48 kHz, 16-bit PCM. Конкретный формат фиксируется в `voice-capture.constants`.

### 5.3. Рекомендуемые слои

| Слой | Ответственность | Пример путей |
|---|---|---|
| UI-сценарий | Разрешения, инструкции, запись, прогресс, retry, экран результата | `mobile/features/biometrics/VoiceCaptureFlow.tsx` |
| Захват аудио | Абстракция recorder, формат, длительность, временный файл | `mobile/lib/biometrics/voice/audio-capture.adapter.ts` |
| Нативный extractor | Вызов openSMILE, конфиги, feature vector, ошибки extractor | `mobile/modules/neuro-voice-smile/` |
| Продуктовые метрики | Нормализация, индексы, quality flags, mapping в UI | `mobile/lib/biometrics/voice/compute-voice-metrics.ts` |
| Локальная история | Persist сессий, версии, агрегаты, опционально путь к локальному аудио | `mobile/lib/biometrics/voice/voice-session-history.store.ts` |
| Backend sync | Хранение агрегатов и трендов, без raw audio по умолчанию | `backend/src/...` |

### 5.4. Граница с backend

- Бэкенд хранит **агрегированные метрики**, версию extractor/scoring, quality flags, protocol type и время замера.
- Сырые аудиофайлы по умолчанию не загружаются. Если появится исследовательский режим загрузки аудио, нужен отдельный consent, TTL, шифрование, удаление и явный флаг назначения данных.
- API должен принимать идемпотентный `sessionId`, чтобы повторная синхронизация не создавала дубли.

## 6. Контракт результата

Минимальный JS-контракт результата должен быть стабильным и независимым от конкретного openSMILE config:

```ts
export interface VoiceMeasurementSession {
  id: string;
  capturedAt: string;
  protocolVersion: string;
  extractorId: 'opensmile';
  extractorVersion: string;
  featureSet: 'eGeMAPSv02' | 'ComParE_2016' | 'custom';
  scoringVersion: string;
  durationMs: number;
  quality: VoiceQualityResult;
  metrics: VoiceProductMetrics;
}

export interface VoiceProductMetrics {
  throatTensionScore: number;
  tremorScore: number;
  confidenceScore: number;
  monotonicityScore: number;
  emotionalActivationScore: number;
  vocalStabilityScore: number;
}
```

Сырые feature vectors можно хранить локально для пересчёта формул, но продуктовый UI должен зависеть только от `VoiceProductMetrics` и `quality`.

## 7. Нормализация и скоринг

### 7.1. MVP-скоринг

- Использовать rule-based индексы поверх openSMILE признаков: устойчивость F0, jitter/shimmer, energy variance, pause ratio, voiced ratio, pitch range.
- Каждая метрика возвращает `0..100`, где 100 — выраженность целевого признака или ресурсное состояние в зависимости от названия. Направление шкалы фиксировать в интерфейсе типа и UI-copy.
- Для пользователя показывать короткую интерпретацию и уверенность качества, а не полный набор acoustic features.

### 7.2. Персональный baseline

- Первые 3-5 качественных сессий формируют baseline пользователя.
- Основной продуктовый сигнал — отклонение от собственного baseline, а не сравнение с "средним человеком".
- При смене устройства или микрофона baseline может требовать пересборки или пометки `deviceChanged`.

### 7.3. Будущий ML-слой

- После накопления размеченных данных можно обучить модель поверх openSMILE features.
- ML-модель должна быть отдельным scoring layer с собственным `scoringVersion`.
- Нельзя смешивать extractor version и scoring version: это разные причины изменения результата.

---

## 8. Quality gates

Запись не должна попадать в продуктовый результат, если:

- длительность меньше минимальной для выбранного протокола;
- слишком много тишины или нет речи;
- есть clipping/перегруз микрофона;
- SNR ниже порога;
- пользователь прервал запись;
- extractor вернул неполный feature vector;
- формат аудио не соответствует ожидаемому контракту.

Ошибки качества должны возвращаться как конкретные retry reasons: "слишком шумно", "говорите ближе к микрофону", "запись слишком короткая", "голос не обнаружен".

---

## 9. Приватность, безопасность и юридические ограничения

- Голос — биометрические и потенциально чувствительные данные. Базовая архитектура: **raw audio stays on device**.
- Для локального хранения аудио нужен явный продуктовый смысл. По умолчанию лучше сохранять только агрегаты и удалять временный файл после extraction.
- Если локальное аудио сохраняется для истории, оно должно иметь TTL и понятную кнопку удаления.
- В UI и документации избегать медицинских формулировок: система оценивает акустические признаки и эмоциональные маркеры, но не ставит диагнозы.
- Для исследований с raw audio требуется отдельный consent и отдельная политика хранения.

---

## 10. Нефункциональные требования

- **Latency:** extraction одной короткой сессии должен укладываться в несколько секунд на средних устройствах.
- **Battery / CPU:** запускать extractor только после завершения записи, не держать постоянный real-time анализ в MVP.
- **Offline-first:** запись, анализ и локальная история работают без сети.
- **Reproducibility:** одинаковый audio input + версии extractor/scoring дают одинаковый результат.
- **Observability:** логировать только технические события и агрегаты качества, без raw audio и текста речи.
- **Regression set:** держать набор обезличенных тестовых WAV для проверки качества после обновления openSMILE/config/scoring.

## 11. Этапы внедрения

1. Зафиксировать протоколы записи, формат WAV/PCM, quality gates и продуктовые метрики MVP.
2. Сделать UI flow записи в `mobile/features/biometrics` с адаптером захвата и локальным сохранением сессии.
3. Интегрировать нативный модуль openSMILE и вернуть стабильный feature vector в JS.
4. Реализовать rule-based scoring layer и экран результата.
5. Добавить историю голосовых сессий и baseline пользователя.
6. Подготовить backend sync агрегатов: идемпотентная запись, версии, quality, без raw audio.
7. Собрать regression dataset и тесты для scoring formulas.
8. После накопления данных рассмотреть ML-скоринг и персонализацию рекомендаций.

## 12. Открытые решения перед разработкой

- Какой протокол MVP берём первым: sustained vowel + fixed phrase или сразу добавляем free speech?
- Храним ли локальный audio artifact после extraction или удаляем всегда?
- Нужна ли расшифровка речи? Для текущей бизнес-задачи openSMILE не требует ASR, а отказ от ASR снижает риски приватности.
- Как формулируем шкалы: "напряжение/дрожание/монотонность" или более мягкие "стабильность/выразительность/уверенность"?
- Где будет первый исследовательский стенд openSMILE: мобильный модуль сразу или backend/Python prototype для быстрой валидации формул?
